# 移植踩坑记录

> 每条按"现象 → 原因 → 解决"记录,面试可展开讲定位过程。

## 1. DHT11 引脚重映射

- **现象**:正点原子原项目 DHT11 用 GPIO1_IO03,韦东山板上该引脚未引出
- **原因**:底板设计差异,原理图查证 J5 扩展口 pin15(CSI_DATA0)= GPIO4_IO21 可用
- **解决**:设备树加 dht11 节点,pinctrl 复用 CSI_DATA00;同时确认 CSI 节点不冲突

## 2. compatible 不匹配导致 probe 不执行

- **现象**:驱动 insmod 成功但 `/dev/dht11` 不出现
- **原因**:设备树节点 compatible 改成 `my,dht11` 后,驱动 of_device_id 宏没同步,platform 总线匹配不上
- **解决**:设备树 compatible 与驱动 `of_match_table` 必须一致——这是设备-驱动匹配机制的标准案例

## 3. dtb 部署不生效

- **现象**:新编译的 dtb 拷到板子后重启无效果
- **原因**:uboot 按固定文件名加载 dtb;boot 分区(实测 /dev/mmcblk1p2)里旧文件未同名覆盖
- **解决**:备份旧 dtb → 同名覆盖 → sync → reboot;验证 `ls /proc/device-tree/` 看节点

## 4. i2cdetect 扫错总线

- **现象**:`i2cdetect -y 1` 上找不到 AP3216C(0x1E),只看到 0x1a(UU)和 0x5d(UU)
- **原因**:韦东山板 aliases 映射 `i2c0 → &i2c1`、`i2c1 → &i2c2`——扫的是 I2C2(声卡 wm8960 + 触摸 gt9xx)
- **解决**:AP3216C 挂在 I2C1 = `/dev/i2c-0`,`i2cdetect -y 0` 看到 0x1E
- **面试点**:用"0x1a 是声卡"反推总线映射的定位思路

## 5. PHY 驱动匹配机制与 I2C 设备不同

- **现象**:PHY 节点的 compatible 是通用的 `ethernet-phy-ieee802.3-c22`,不是 `smsc,lan8720a`
- **原因**:PHY 驱动匹配靠 **phy_id**(读 PHY ID 寄存器,LAN8720A = 0x0007c0f0),不靠 compatible
- **面试点**:MAC 靠 compatible、PHY 靠 phy_id,两条匹配机制对比

## 6. 板上无 nc/busybox

- **现象**:测试 TCP 服务时板上没有 nc 命令
- **解决**:真 bash 自带 `/dev/tcp`:`exec 3<>/dev/tcp/127.0.0.1/9000` + `timeout 3 cat <&3`

## 7. veh_term_service 端口占用

- **现象**:重启服务报 `bind: Address already in use`
- **原因**:旧进程没死(后台 `&` 运行)
- **解决**:`killall veh_term_service`;驱动侧 SO_REUSEADDR 已处理 TIME_WAIT

## 8. QT 上屏环境变量繁多

- **现象**:QT 应用运行前需手敲 9 条 export(XDG_RUNTIME_DIR/QT_QPA_PLATFORM=linuxfb/tslib 系列)
- **解决**:固化为 run.sh 启动脚本;linuxfb 直写 framebuffer、tslib 处理触摸校准(QT_QPA_FB_DISABLE_INPUT=1 防双通道抢输入)

## 9. "千兆 PHY"名不副实

- **现象**:项目大纲写"千兆网络 PHY",实测板载 LAN8720A 为百兆 RMII
- **结论**:深挖按百兆讲,含金量不变(RGMII/千兆是 RK 平台后续升级项)
